ADR-014 · user management in local identity mode · 16 September 2026

who owns the user

Every component that touches a Vaullet user, what passes between them, and which of them holds the record that decides. The short version is that two systems hold two different objects about the same person, and almost every design mistake here comes from treating them as one.

Keycloak owns the identity. Vaullet owns the account.

Keycloak holds the person who logs in — credentials, MFA, email, name, roles. Vaullet holds the thing money is keyed to: an account_id, a status, and a reference back. Neither is a copy of the other, so neither can go stale against the other, and there is no reconciliation job anywhere in this design.

every component and every edge

the map

User management adds no new service. It is a capability of Auth Service, switched on by auth.provider: local, and it is the only Vaullet-written component on this page. Everything else here already exists for other reasons.

the rule

who owns which fact

One rule settles every field: whoever owns a fact's failure mode owns the fact. If getting it wrong is an authentication problem, it is Keycloak's. If getting it wrong is a money problem, it is ours.

What Keycloak holds

The person who logs in. It is replaceable in principle — and the anchor is what makes replacing it survivable — but while it is there, it is the only authority on identity.

  • The complete credential and session story
  • Whatever profile the operator collects at registration
  • Realm roles, and the hosted pages users see

It never learns a balance, and never learns that an account was frozen for fraud.

What Vaullet holds

Four columns. That is the entire user record on our side, in both modes, and it is deliberately too boring to be worth breaching.

  • account_id — permanent, and the only thing money knows
  • keycloak_sub — nullable, because an account can exist before an identity does
  • external_ref — the operator's id, unique, never updated
  • status — ACTIVE, SUSPENDED or CLOSED

No email, no name, no date of birth, no document. Under federation that is a selling point; under local mode it is just restraint.

the awkward operation

creating an account

Everything else on this page is a single call to a single system. Creating a user is three writes across two systems with no transaction spanning them, so it is the one place the split costs something. The answer is not a distributed transaction; it is that every step is idempotent and the repair already exists.

The anchor, as ADR-014 amends it

Three changes to what ADR-006 wrote, each closing an open item: keycloak_sub becomes nullable so an account can be provisioned before its user has ever logged in (B2), external_ref gets the column its promises need (B3), and LOCKED becomes SUSPENDED — both because ADR-012 already published that word to operators, and because "locked" is what Keycloak calls a user it has temporarily locked out after too many bad passwords, which is a different thing entirely.

CREATE TABLE accounts (
    account_id    UUID PRIMARY KEY,
    keycloak_sub  UUID        NULL,        -- null while unlinked; set at first authentication
    external_ref  TEXT        NULL,        -- operator's own user id; immutable once set
    status        TEXT        NOT NULL CHECK (status IN ('ACTIVE','SUSPENDED','CLOSED')),
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (keycloak_sub),
    UNIQUE (external_ref)
);

the freeze path

This is the one sequence that explains the whole design. It runs identically in both modes, it never asks the operator's directory for permission, and it is the reason the status column cannot live in Keycloak.

the two ways of managing users

local against federated

User management is not something an operator buys. It arrives with auth.provider: local and is unavailable under federated, where the operator's own directory does the job. What matters is how little else differs.

The freeze sits on PATCH /v1/accounts/{id} and user administration sits on the sub-resources, so the two are different endpoints held by different roles with different audit trails. ADR-006's separation of duties comes out of the URL layout rather than being enforced on top of it.

before anyone writes code

what exists, and what comes first

Build order

  • The anchor. Migration, repository, POST and GET /v1/accounts, the by-ref lookup. Federated mode is complete here, and the ledger finally gains a creator for the account row it has never had one for.
  • Token validation, the account_id protocol mapper, and just-in-time provisioning.
  • Status enforcement and the Redis-cached gateway check.
  • The Keycloak admin client and the identity sub-resources — the subject of this page.
  • Machine clients and token exchange, which nothing else depends on.

Deliberately not now

  • A local read projection. Rejected as ADR-014's first alternative, with a named trigger: an admin user list slower than about a second, or a filter spanning status and a profile field. Writes are identical either way, so it stays a pure addition.
  • Bulk import. A migrating operator needs it and will drive a per-user REST loop until it is designed.
  • End users editing their own profile — that is Keycloak's account console, not our API.

One question ADR-014 does not settle: whether self-service registration should point at Keycloak's hosted pages, which is the default and needs no code, or run through POST /v1/accounts. If the hosted pages are good enough for a local-mode operator, the API surface here is admin-facing only, and that is a considerably smaller thing to build than "user CRUD" suggests.
